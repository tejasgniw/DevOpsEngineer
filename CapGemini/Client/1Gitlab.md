## How you structure .gitlab-ci.yml

```
stages:
  - build
  - test
  - package
  - deploy

variables:
  IMAGE_NAME: registry.gitlab.com/$CI_PROJECT_PATH/my-app
  IMAGE_TAG: $CI_COMMIT_SHA
  DOCKER_TLS_CERTDIR: ""

default:
  image: docker:24.0
  services:
    - docker:24.0-dind

# -----------------------------
# BUILD STAGE: Builds Docker image and stores it as an artifact for reuse in later stages.
# -----------------------------
build:
  stage: build
  script:
    - docker build -t $IMAGE_NAME:$IMAGE_TAG .
    - docker save $IMAGE_NAME:$IMAGE_TAG -o image.tar
  artifacts:
    paths:
      - image.tar
    expire_in: 1 hour

# -----------------------------
# TEST STAGE: Loads built image and runs automated tests inside the container.
# -----------------------------
test:
  stage: test
  needs:
    - build
  script:
    - docker load -i image.tar
    - docker run --rm $IMAGE_NAME:$IMAGE_TAG npm test

# -----------------------------
# PACKAGE STAGE: Logs into GitLab Container Registry and pushes the validated image.
# -----------------------------
package:
  stage: package
  needs:
    - build
    - test
  script:
    - echo $CI_REGISTRY_PASSWORD | docker login -u $CI_REGISTRY_USER $CI_REGISTRY --password-stdin
    - docker load -i image.tar
    - docker push $IMAGE_NAME:$IMAGE_TAG
  rules:
    - if: $CI_COMMIT_BRANCH

# -----------------------------
# DEPLOY STAGE (HELM): Uses Helm to upgrade or install the application into Kubernetes, injecting the new image tag dynamically.
# -----------------------------
deploy_staging:
  stage: deploy
  image: alpine/helm:3.13.0
  needs:
    - package
  before_script:
    - mkdir -p ~/.kube
    - echo "$KUBE_CONFIG" > ~/.kube/config
  script:
    - helm upgrade --install my-app ./helm/my-app \
        --namespace staging \
        --create-namespace \
        --set image.repository=$IMAGE_NAME \
        --set image.tag=$IMAGE_TAG
  environment:
    name: staging
  rules:
    - if: $CI_COMMIT_BRANCH == "staging"
 # ------------------------------------------------     
deploy_prod:
  stage: deploy
  image: alpine/helm:3.13.0
  needs:
    - package
    - deploy_staging
  before_script:
    - mkdir -p ~/.kube
    - echo "$KUBE_CONFIG" > ~/.kube/config
  script:
    - helm upgrade --install my-app ./helm/my-app \
        --namespace production \
        --create-namespace \
        --set image.repository=$IMAGE_NAME \
        --set image.tag=$IMAGE_TAG
  environment:
    name: production
  rules:
    - if: $CI_COMMIT_BRANCH == "production"
      when: manual
```

## How you handle multi-stage pipelines

I design multi-stage pipelines with **clear separation** of concerns across build, test, package, and deploy stages. **Each stage acts as a quality gate**, ensuring the **next stage only runs if the previous one succeeds**. I also **use needs to create controlled job dependencies** and optimize execution flow.

## How you manage different environments (dev/qa/prod)

I manage dev, QA, and production environments using quality-gates such as **branch-based rules**, **protected GitLab environments**, **k8s namespace**, **protected variables**, and **controlled promotion between stages**. Staging deployments are automatic for validation, while **production requires manual approval**. This ensures safe promotion, environment isolation, and full deployment traceability.

## How you use:

### Runners

Runners execute the pipeline jobs. I configure runners based on workload type and isolation needs.

- Use Docker executor for container builds (isolated, reproducible)
- Use Shell executor for Windows/.NET Framework if needed to test locally (Insecure for staging and prod)
- Tag runners for workload separation (e.g., k8s-runner, windows-runner)
- Restrict production runners to protected branches

To restrict runners to protected branches (primarily in GitLab), edit the specific runner in the project's Settings > CI/CD > Runners and check the "Protected" checkbox. This ensures the runner only picks up jobs from branches defined as protected (e.g., main), protecting sensitive deployment credentials.

🔥 Good addition:
- For production deployments, I prefer dedicated runners with restricted access. (using tags/protected branch)


### Artifacts

- Files generated by a job that are stored and passed to later jobs/stages.
- I use artifacts to ensure consistency across stages. The same Docker image built in the build stage is reused in test and package stages, preventing rebuild drift.

### Cache

Stores dependencies between pipeline runs to improve speed.

- Artifacts = pipeline outputs
- Cache = dependency acceleration

```
cache:
  paths:
    - node_modules/
```

- Speeds up builds
- Reduces dependency installation time
- Improves pipeline performance

I use cache to speed up dependency installation and optimize pipeline runtime without affecting artifact integrity.


### Variables

I use CI/CD variables to externalize configuration and securely manage secrets. Production variables are protected and restricted to protected branches.

- To conditionally check against a version.


### Protected branches

- Only approved users can push
- Required MR approvals
- Production deploy only allowed from protected branch

I protect main and release branches to enforce code review, approval workflows, and safe production deployment.


### Manual approvals

```
when: manual
```

- Adds human validation
- Prevents auto-production releases
- Allows business approval

You can also configure:

- Required approvers
- Environment protection rules

Production deployments require manual approval to ensure governance and reduce risk. This adds a controlled release checkpoint after staging validation.

#### protected branches control who can modify code in the repository, while protected environments control who can deploy that code to specific targets


# Tricky questions

## 1. What’s the difference between needs and dependencies?

- needs defines job execution order and creates a DAG (Directed Acyclic Graph) pipeline.
- dependencies controls which artifacts are downloaded from previous jobs.

If **needs is defined, GitLab automatically handles artifact passing** unless overridden.

## 2. How do you prevent two production deployments from running at the same time?

```
deploy_prod:
  stage: deploy
  resource_group: production
```

This ensures:

- Only one job for that resource runs at a time
- Prevents deployment race conditions

## 3. If your pipeline is very slow, how would you optimize it?

- Use **needs** for parallelism
- Use cache for dependencies
- Use smaller Docker base images
- Enable Docker layer caching
- Split monolithic jobs into smaller **parallel** jobs
- Use artifacts efficiently
- Use big size runners if available

## 4. How would you rollback a bad production deployment?

```
helm rollback my-app 1
```

- Helm rollback to previous revision.
- Automatic rollback during upgrade/install (--atomic/--rollback-on-failure), which is even better
- Redeploy previous image tag with a job for it.
- Maintain versioned image tags.
- Use Git tags for release tracking or semantic versioning.
- GitLab Environments: Use the built-in "Rollback" button in GitLab environments, which triggers a previous successful pipeline.

```
helm upgrade [RELEASE_NAME] [CHART_PATH] --rollback-on-failure --timeout 5m
```

## 🔥 5. How do you ensure the image tested is exactly the one deployed?

I build once, tag with commit SHA, store as artifact, and reuse the exact same image across test, package, and deploy stages. I never rebuild in later stages.


## 🔥🔥6. How would you redesign this pipeline for a multi-microservice architecture?

- Separate pipelines **per service**
- Use **parent-child** pipelines
- Use template **includes**
- **Version images** independently
- Use dynamic environments
