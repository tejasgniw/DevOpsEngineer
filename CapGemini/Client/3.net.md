# .net automation

I structure the pipeline with **restore, build, test, and publish stages**. I **separate build from deployment to ensure artifact immutability**. Deployment depends on the target — IIS for legacy apps, Windows services, or containerized images for modern .NET Core applications. I **manage environment-specific configuration via variables and secure secrets, and enforce manual approvals for production** releases.

# 1. Understand .NET Build Basics

Typical commands:

```
dotnet restore
dotnet build
dotnet test
dotnet publish
```

What they do:

- restore → downloads dependencies
- build → compiles code
- test → runs unit tests
- publish → creates deployable output


- In GitLab, I use a multi-stage pipeline separating restore, build, test, and publish steps to ensure clean validation before deployment.



# 2. Deployment Options

Understand the common targets:

## 1️⃣ IIS (classic .NET Framework)

- Publish output
- Deploy to Windows Server
- Use Web Deploy or PowerShell

## 2️⃣ Windows Server (service/app)

- Publish
- Copy artifact
- Restart service

## 3️⃣ Containerized (.NET Core / .NET 6+)

- Build Docker image
- Push to registry
- Deploy to Kubernetes

- For modern workloads, I prefer containerized deployments for consistency across environments.



# 3. CI/CD & Environment Strategy

Be ready to explain:

## Separate build & deploy stages

- Build once
- Deploy same artifact to all environments

## Environment-based configs

- Use appsettings.{Environment}.json
- Or environment variables
- Avoid hardcoding secrets

## Artifact management

- Store published output
- Reuse in deploy stage
- Ensures immutability

## Safe deployments

Dev → QA → Prod promotion

- Manual approval for production
- Protected variables based on environments
- Protected branches
- protected environments
